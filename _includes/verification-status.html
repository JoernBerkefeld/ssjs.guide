{% comment %} Renders a single page-level verification-status badge. Status values (front matter `verification:`): verified - every method/constructor/property on the page is runtime-verified (green) in-progress - some but not all are verified (yellow) pending - none verified yet, or field absent (grey; default) The page's own `verification:` front matter is the source of truth for BOTH leaf pages and overview (index) pages. Overview pages are cross-listed in _data/navigation.yml (a page can appear under several sections — e.g. HTTP.Get is listed under both /http/ and /core-library/), so a URL-prefix scan cannot reliably find an overview's children. The verify-ssjs-guide-docs skill computes and writes each overview's `verification:` (and `differs_from_docs:`) explicitly from navigation.yml membership. Only when an overview page has NO explicit `verification:` field do we fall back to aggregating URL-prefix children (legacy behaviour), skipping jekyll-redirect-from stubs (which carry a `redirect` object and no `verification` field). An overview page can opt OUT of that aggregation with `aggregate_verification: false`. Aggregation only ever describes the CHILD pages — it says nothing about the overview's own hand-written prose, tables, and code samples, which no test script covers. On a page whose prose is unreviewed, an aggregated green badge claims a review that never happened, so the opt-out forces the honest "pending" default instead. Removing `verification:` alone is NOT enough: without the opt-out the page silently falls through to aggregation and goes green again. A third, independent badge is driven by front matter `test_scripts: complete`. It signals that EVERY chapter on the page carries a "Show test script" details block whose assertions prove all documented claims (positive, negative, and deviation). It is never aggregated from children — the verify-ssjs-guide-docs skill sets it per page only after a fully green run. NARRATIVE pages (language/, recipes/, best-practices/, getting-started/) have NO ssjs-data entry, so `verification:` — which mirrors ssjs-data `isConfirmed` — can never apply to them. They use the SEPARATE front matter key `claims_verified: true` instead, rendered as its own purple "Claims checked" badge. It states that the prose/examples on the page were checked, NOT that a catalog entry was runtime-confirmed. The two keys are mutually exclusive: a page carrying `verification:` ignores `claims_verified` entirely, so the narrative key can never be mistaken for (or silently upgrade into) the ssjs-data-backed "Runtime verified" badge. {% endcomment %} {% assign status = "pending" %} {% assign differs = false %} {% comment %} Narrative mode: no `verification:` key (nothing in ssjs-data to mirror) but the page's claims were checked.
